# Session Logs — 会话日志（每日交接）

> AI 每次新会话启动，必须 Read 最新一份 session log。
> 这是跨会话的**短期记忆**，避免重复劳动 / 误删昨天的工作 / 忘记关键决策。

---

## 作用

记录每次重大会话的**实际改动 + 关键决策 + 待办**，让下一次会话能从断点接续。

与其他文档的分工：

| 文档 | 时间范围 | 内容 |
|------|---------|------|
| `lessons.md` | 永久 | "踩过的坑"，跨项目通用经验 |
| `specs/*.md` | 永久 | 业务规则规约 |
| `session_logs/YYYY-MM-DD.md` | 单日 | 当天具体改了什么、决定了什么 |
| `contracts/` | 永久 | API 契约冻结 |

---

## 文件命名

```
docs/session_logs/YYYY-MM-DD.md            # 普通日志
docs/session_logs/YYYY-MM-DD-<topic>.md    # 同一天有多次重大会话时加副标题
docs/session_logs/_template.md             # 模板
```

---

## 何时写

- 单次会话产生 ≥ 3 个 commit
- 单次会话产生 ≥ 1 个新业务规则确认
- 单次会话踩到新坑（同步加到 lessons.md）
- 单次会话留下未完成的 TODO（必须写日志，否则下次会话不知道）
- 涉及部署 / 迁移 / 数据修改等高风险操作

不需要写：

- 单纯问答 / 解释 / 阅读代码（没改东西）
- 5 分钟的小修复（提交信息已足够）

---

## 写日志的纪律

1. **按事实写**：改了什么文件、跑了什么命令、看到什么输出
2. **明确未验证**：哪些场景没测、哪些环境没部署、哪些假设没确认
3. **附待办**：留给下一次会话的明确任务
4. **附风险**：本次改动可能在哪里出问题，下次需要观察什么
5. **附部署计划**（如适用）：内网 / 生产怎么 deploy、回滚怎么做

---

## 启动协议中的位置

```
新会话启动
  ↓
Step 2: Read docs/session_logs/ 下最新 1 个文件
  ↓
AI 看到：上次改了什么、有什么待办、有什么坑
  ↓
AI 复述给用户："上次我们做到 X，今天的任务是 Y，对吗？"
  ↓
用户确认 → 继续工作
```
