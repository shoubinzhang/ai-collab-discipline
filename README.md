# AI Collaboration Discipline Demo

> 一套已经在真实生产项目（中大型合规软件）验证过的
> **AI 辅助开发协作纪律框架**。
>
> 核心信念：AI 协作的瓶颈不在模型能力，在使用者能否设计出
> **正确的协作协议 + 自动化执行机制**。

---

## 故事 — 为什么有这个框架

**背景**：项目跑到中后期，开始出现 AI 辅助开发的典型失败模式：

- 文件越改越大（最大单文件突破 3000 行）
- AI 顺手删除现有功能（"看起来冗余"）
- 修一个 bug 引出三个新 bug
- 对需求"降级处理"（用户要 9 份详细文档，AI 写 1 份详细 + 8 份精简）

**关键洞察**：问题的根因不是模型能力不够，而是**没有给 AI 设计足够明确的边界**。
AI 默认倾向于"帮你想得更多"，但在工程项目里，"自作主张"等于"引入隐患"。

**对策** — 设计一套 6 层纪律框架：

| 层 | 名称 | 解决什么 |
|----|------|---------|
| **L1** | 协议层 | 一份强制加载的项目协议文件，定义会话启动流程、若干绝对禁令、文件规模红线 |
| **L2** | Harness 层 | 通过 AI 工具的 hook 机制，把代码验证、迁移检查、会话交接做成自动触发，**无法跳过** |
| **L3** | 知识层 | 业务规约、踩坑记录、会话日志**三件套**，强制每日交接闭环 |
| **L4** | CI 门禁层 | 自定义脚本把「文件规模红线」「API 契约漂移」等纪律变成 **CI 失败** |
| **L5** | 代码契约层 | 合约测试 + JSON Schema 双保险，**冻结** API 响应结构 |
| **L6** | 运行时层 | 7 层中间件覆盖审计、认证、幂等、安全、限流、防护、性能 |

**效果**：执行这套约束后，AI 输出从"能跑但风险高"变成"**敢直接合并到生产分支**"。
同一个 AI 模型，在不同纪律框架下产出质量差距巨大。

**结论**：AI 协作的瓶颈不在模型能力，而在使用者能否设计出正确的协作协议 +
自动化执行机制。这是一种**新的工程能力**。

## 6 层架构图

```
┌──────────────────────────────────────────────────────────────────┐
│ L6  运行时层      7 层中间件（审计/认证/幂等/安全/限流/防护/性能）│
├──────────────────────────────────────────────────────────────────┤
│ L5  代码契约层    合约测试 + JSON Schema · 冻结 API 响应结构      │
├──────────────────────────────────────────────────────────────────┤
│ L4  CI 门禁层     文件规模检查 / 契约漂移检测 / 测试覆盖率门禁    │
├──────────────────────────────────────────────────────────────────┤
│ L3  知识层        业务规约 / 踩坑记录 / 会话日志（三件套）        │
├──────────────────────────────────────────────────────────────────┤
│ L2  Harness 层    Claude Code hooks / agents / settings.json      │
├──────────────────────────────────────────────────────────────────┤
│ L1  协议层        CLAUDE.md（启动协议 / 改代码纪律 / 5 条禁令）   │
└──────────────────────────────────────────────────────────────────┘
```

每一层接住一类典型失败：

| 层 | 失败模式示例 | 接住方式 |
|----|------------|---------|
| **L1 协议层** | AI 跳步、不读 spec 直接编码 | 启动协议强制按顺序读 6 类文档 |
| **L2 Harness** | AI 失忆、跨会话忘约定 | SessionStart hook 自动加载上下文 |
| **L3 知识层** | 同一个 bug 重复犯 3 次 | lessons.md 沉淀，每次会话必读 |
| **L4 CI 门禁** | 单文件 3000 行 / 契约偷偷改 | 脚本作为 CI step，新增违规 PR fail |
| **L5 代码契约** | 后端字段重命名打挂前端 | 合约测试在改 schema 时立即报警 |
| **L6 运行时** | 高危操作没审计 / 没鉴权 | 中间件栈强制覆盖每个请求 |

## 快速试用

### 1. Clone 并初始化

```bash
git clone <this-repo> my-project
cd my-project
chmod +x .claude/hooks/*.sh
```

### 2. 跑一遍 CI 检查（验证环境）

```bash
python3 scripts/ci/check_file_size_limits.py --report
python3 scripts/ci/check_contract_drift.py --help
```

### 3. 在 Claude Code / Cursor 里打开仓库

打开新会话时，AI 会被 CLAUDE.md 强制按以下顺序读：

1. `CLAUDE.md`（L1 协议）
2. `docs/session_logs/` 最新一份（上次会话状态）
3. `docs/lessons.md`（避免重犯已知陷阱）
4. `docs/specs/README.md`（业务规则索引）
5. **任务相关的具体 spec**（按需）
6. **实际代码**（grep / read，不凭记忆）

然后 AI 会**用中文复述理解**等你确认，**再动手编码**。

### 4. 改代码时

每次编辑，Claude Code 的 hook 自动触发：

- `PreToolUse Edit` — 检查目标文件行数（超警戒线警告，超硬上限拒绝）
- `Stop` — 检查未提交改动（避免 AI 改完忘 commit）

CI 端：

- 每个 PR 自动跑 `check_file_size_limits.py`，新增违规文件直接 fail
- 契约文件改动需配套契约测试更新

## 这套框架解决的真实问题

这个 demo 是从一个**已部署到生产环境**的合规软件项目抽象提炼出来的。原项目曾经遭遇的典型坑（已脱敏）：

- 多个前端页面突破 2000 行（最大超过 3000 行），形成"冻结文件"——再加功能只会更烂，拆分成本越来越高
- 单次会话里 AI 把 9 份详细设计文档擅自降级成 8 份精简版（没请示）
- 同一个 React Hook 顺序 bug 在 3 个月内触发 3 次（没 lessons 沉淀）
- 数据库 schema 与代码不同步，导致生产 500 错误（没强制读 spec）
- 后端 API 字段重命名上线后前端立刻挂了（没契约测试）

每一个坑都被本框架的某一层接住了。**这不是理论文档，是手术后的复盘**。

## 核心理念

### 「单一真相源」原则

每类信息只能有一个权威来源：

- **业务规则** → `docs/specs/`
- **失败教训** → `docs/lessons.md`
- **会话状态** → `docs/session_logs/最新.md`
- **API 契约** → `docs/contracts/` + 合约测试

AI 不许凭记忆推断。改代码前**强制读对应单一真相源**。

### 「文件规模红线」原则

文件规模超标后**禁止加新功能**，必须先拆。这条规则比"代码风格规范"重要 10 倍——
风格不一致只是难看，3000 行文件是真的没法维护。

### 「证据三层」原则

AI 报告必须分清：

- ✅ **已验证** — 附工具输出（grep / build / 测试结果）
- 🔶 **高置信推断** — 附推理链
- ❓ **需确认** — 附具体问题

禁止"应该能工作"、"通常这样"等无证据表达。

### 「禁止降级」原则

AI 做不到原要求时**必须先请示**，不许擅自精简、删条目、降版本。

### 「契约即冻结」原则

API 响应结构一旦写进 `docs/contracts/`，就用 JSON Schema + 合约测试**双锁定**。
改字段必须同步改契约 + 改测试 + 升版本号。

## 适用场景

✅ **适合**：

- 非科班开发者长期维护的项目（生物医药 R&D / 行业专家 + AI 辅助）
- 多人协作但代码质量良莠不齐的团队
- 合规要求强（GMP / GxP / 医疗器械 / 金融）的项目
- 想用 AI 加速但又怕失控的团队

⚠️ **不适合**：

- 一次性脚本 / 一周内交付完丢的项目
- 团队已经有非常成熟的工程文化、不需要 AI 协作约束
- 完全 prototype 阶段、规则尚未稳定
